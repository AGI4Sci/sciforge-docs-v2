# Pasilla RNA-seq 三人协作

本案例用一个报告任务演示三人协作：A 负责需求与评审，B 计算计数质控和子集 CPM，C 使用 B 已采纳的结果做描述性比较。重点是把工作交给成员、评审某一版成果，再把它传给下游。

首次使用请先完成[协作使用说明](../features/collaboration.md)中的登录、设备连接和模型准备。

本页截图来自一次真实的三账号协作演示，完整展示了需求确认、成员交付、返修、采纳、下游接力与结项。

## 输入与分工

数据来自 [Bioconductor pasilla](https://bioconductor.org/packages/release/data/experiment/html/pasilla.html) 公开果蝇 RNA-seq 计数数据。演示使用原始表头和前 **50 个基因 × 7 个样本**，保持顺序及数值不变，配套使用样本注释。

这 50 行是原表顺序摘录，不是代表性抽样。子集 CPM 的分母仅为每个样本这 50 个基因的计数之和，不是完整测序文库大小，不用于全转录组归一化或显著性检验。

| 人员 | 工作 | 本轮交付 |
| --- | --- | --- |
| A：负责人 | 确认需求、邀请成员、调整派单、返修、采纳和结项 | 两项采纳记录及项目总结 |
| B：成员 | 计算 7 个样本的摘录总计数和 50 基因的子集 CPM | 两版 README，以及独立的 member-qc-notes.md 成员说明 |
| C：成员 | 读取 B 已采纳的第 2 版，比较 treated / untreated 组均值 | 一版描述性比较 README |

跟随案例操作时，先从公开来源准备计数数据和样本注释，再将输入提供给项目。

## 1. A 写需求并确认两个串行模块

A 在需求页写入真实摘录、输出范围和依赖：B 先出 QC 与子集 CPM 报告；C 只使用 B 被采纳的版本。补全后，A 检查模块，再确认需求。

可参考以下目标写法，并在输入区域补齐实际数据和样本注释：

```text
模块 1：根据所附 50 基因 × 7 样本计数，报告每样本的摘录总计数、
子集 CPM、零计数比例和列和校验。README 包含方法、可复算代码和限制。
允许成员另附自己的检查说明，由负责人预览和评审。

模块 2：依赖模块 1 已采纳的结果，读取其报告和成员说明，比较
 treated 与 untreated 组的平均子集 CPM，列出绝对均值差最大的 5 个基因。
只做描述性比较，不报告 p 值、FDR 或显著性结论。
```

![真实需求补全生成 QC 和下游描述性比较模块，等待负责人确认](/img/docs/collaboration/requirements-ready.png)
*图 1：输入、输出范围和依赖写进任务说明，供成员接单前阅读。*

**观察点**：C 的模块依赖 B 已采纳的成果，不能把“B 的 AI 写完了”当作下游启动条件。

## 2. A 邀请成员并把模块 1 分配给 B

确认需求后，A 邀请 B、C 加入，并检查任务分配。系统初始分配与目标分工不同，A 通过界面把模块 1 改派给 B；B 阅读任务后接受。

![B 的任务处于待开始，模块 2 显示等待上游采纳](/img/docs/collaboration/task-offer.png)
*图 2：模块 1 的成员为 B；模块 2 留在收集箱，等待模块 1 采纳。*

**观察点**：以任务卡上的成员和状态为准，不要只根据自然语言分工推断派单结果。

## 3. B 检查草稿并提交两份文件

本机 AI 生成 README 后，B 预览报告，通过**添加资料 → 从本机上传**加入 member-qc-notes.md，并编辑结果说明。第 1 版清单包含 AI README 和成员说明两项。

![B 的第 1 版草稿列出 AI 报告和成员说明](/img/docs/collaboration/delivery-draft.png)
*图 3：成员审阅后确认提交，附加说明作为独立文件保留。*

提交前，B 检查了 350 个子集 CPM 数值，并在结果说明中记录计算方法、核对结果和需要负责人评审的内容。

**操作要点**：提交前同时检查文件正文和结果说明，确保数值、文字及本次完成内容一致。

## 4. A 提出返修，B 提交第 2 版

A 预览封存的第 1 版，通过**要求修改**让 B 更正评审状态描述、保留独立说明，并增加每样本零计数数量、比例和 CPM 列和校验。

B 修改后重新审阅、提交第 2 版，A 预览这一版并采纳。第 1 版仍保留在历史中。

![第 2 版交付说明记录修改内容，下方保留第 1 版历史](/img/docs/collaboration/delivery-history.png)
*图 4：新版用于本次评审，旧版仍可展开查看。*

**观察点**：返修形成新的交付版本；采纳前应明确预览的是哪一版。

## 5. C 接受下游任务并读取已采纳结果

B 第 2 版被采纳后，模块 2 才具备派单条件。A 在接单前将该模块调整给 C，C 接受并执行。系统把 B 第 2 版 README 和成员说明放入 C 的任务输入，无需手动复制。

![C 正在执行模块 2，任务说明要求读取已采纳的第 2 版及成员说明](/img/docs/collaboration/upstream-input.png)
*图 5：项目已采纳 1/2，下游 C 正在执行。*

下游使用 B 已采纳的第 2 版文件，C 可以直接在自己的任务中读取这些输入并继续分析。

## 6. C 预览报告，A 采纳并结项

C 预览报告，确认只使用已采纳输入并保留描述性分析限制，再提交。A 预览 C 的封存报告并采纳，全部模块完成后填写总结、确认结项。

![C 在任务会话中预览 treated 与 untreated 子集 CPM 比较报告](/img/docs/collaboration/report-preview.png)
*图 6：报告限定数据范围，不把均值差解释为统计显著性。*

![项目最终显示已完成和已采纳 2/2](/img/docs/collaboration/project-completed.png)
*图 7：两个模块均完成，项目本身也已结项。*

## 案例成果

| 环节 | 完成结果 |
| --- | --- |
| 需求补全与确认 | 两个带依赖的真实工作模块 |
| 审阅与添加资料 | AI README 与成员说明一起封存 |
| 返修与版本保留 | B 两版交付，A 采纳第 2 版 |
| 下游接力 | C 使用 B 已采纳的第 2 版报告及成员说明 |
| 人工采纳与结项 | 两模块采纳，项目最终已完成 |

本案例展示了从需求到交付的完整协作流程。分析采用数据摘录和描述性比较，阅读结果时应结合相应的数据范围与方法。
