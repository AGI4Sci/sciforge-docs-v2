# 文档维护清单

用户教程只在 `sciforge-docs-v2` 维护。客户端仓库保留网站入口、安装开发说明和内部补充，不再复制完整教程。

## 1. 固定本轮版本

先记录最新客户端主线的日期和提交，再核对改动涉及的界面、配置、包版本及操作。更新[版本与兼容性](../reference/version-and-compatibility.md)和仓库 README；公开源码的提交单独记录，不等它更新后才写手册。

读取当前实现，不只看旧 README、测试名称或计划文档。某项行为只有测试预期、实际调用却未接入时，把它列为待核对项，不能写成操作步骤。

## 2. 更新正文与导航

- 先写“在哪里打开、怎么操作、得到什么结果”，再写影响操作的限制。
- 使用界面的实际名称。不要在每页重复主线提交、权限术语和验证说明，统一链接版本页即可。
- 功能迁移时调整总览、侧栏和相关链接；旧 URL 保留简短迁移说明，移出当前功能导航。
- 不按目录数量宣称“所有插件可用”；内置模块、独立插件、Skill 和 MCP 分别说明。
- 截图和案例保留原日期与版本。没有重录就不改称新版演示；过时画面加一句说明。

## 3. 检查公开范围

公开站可介绍最新客户端的用户操作。内部部署、数据库迁移、VPN／SSH 管理、服务端适配、真实账户配置和私有验收资料留在内部文档。客户端登录、设备连接、团队项目等通用用法可以公开。

新图像先检查可见账户、路径、令牌及素材使用权。保留既有已审图片，不从私库批量恢复旧媒体。插件许可证、原作者归属和第三方声明分别保留；文档更新不修改许可证或仓库可见性。

## 4. 保持入口一致

公开和私有客户端首页的用户手册都指向 https://agi4sci.github.io/sciforge-docs-v2/ 。仓内旧手册页保留到对应网站页面的链接。内部补充不进入公开导出。

后续源码导出须保留公开仓库已经审过的许可证、替代素材、安全测试夹具和这些入口，不用私库目录直接覆盖公开仓库。

## 5. 构建与检查

```bash
npm ci
npm run typecheck
npm run build
```

构建会生成搜索索引，并检查站内链接。另检查退役功能是否仍出现在首页、侧栏、搜索推荐和视频章节介绍。构建成功只说明文档可构建，正文还需逐页核对。

视频未重录时保留原文件和章节顺序，在导览页注明适用版本。涉及章节数据时再运行 `node scripts/check-tour.cjs`。

## 6. 发布与抽查

通过 PR 审阅，合并后等待 GitHub Pages 部署成功。在线抽查首页、版本页、功能总览和本次重点页面，确认新内容和页面链接正常。

PR 写清更新依据、主要页面、检查结果及需要后续补拍的截图。出错时用新的 revert PR 回退，不部署更早的站点配置。
